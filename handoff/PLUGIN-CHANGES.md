# plow_chat plugin changes — what & where to apply

The onboarding SKILL in this PR emits three in-band markers (`[[BUBBLE]]`,
`[[PHOTOS:...]]`, `[[PAUSE]]`). **The `plow_chat` platform adapter is what
turns those markers into real iMessages.** Without these plugin changes, the
markers reach the owner as literal text (`[[BUBBLE]]` printed in a message).

This directory ships the change as a patch because the plugin's real home is
**the base image, not this repo**. This repo only overlays a modified copy at
runtime via a `compose.yml` bind-mount (harness-only, not part of any PR).

## Where to apply

- **Repo:** the one that builds the `plow-cloud-agents` base image
  (`public.ecr.aws/e1h7x4a2/plow-cloud-agents`; see `Dockerfile:11` of this
  repo for the exact base tag/digest currently pinned).
- **File:** `plugins/plow_chat/__init__.py` (the file that lands at
  `/opt/hermes/plugins/plow_chat/__init__.py` in the image).
- **Patch:** `handoff/plugin-changes.patch` — a real unified diff of the stock
  base-image plugin vs. the modified one, generated by extracting the stock
  file from the pinned base image
  (`docker run --rm <base> cat /opt/hermes/plugins/plow_chat/__init__.py`) and
  diffing against the harness copy. Apply with `git apply` or
  `patch -p1 < handoff/plugin-changes.patch` from the base-image repo root.
- **After applying:** rebuild + publish the `plow-cloud-agents` base image,
  then bump `Dockerfile:11` `FROM` in this repo to the new base tag/digest.

## What changed vs. stock (all in `plugins/plow_chat/__init__.py`)

### 1. Module constants (top of file)
- `BUBBLE_SENTINEL = "[[BUBBLE]]"`
- `PHOTOS_SENTINEL_PREFIX = "[[PHOTOS:"`
- `PAUSE_SENTINEL = "[[PAUSE]]"`
- `PAUSE_SECONDS = 4.0` — how long a `[[PAUSE]]` marker sleeps.
- `INTER_BUBBLE_SECONDS = 1.0` — human-timing gap inserted between consecutive
  bubbles (core adds no pacing of its own).

### 2. `[[BUBBLE]]` text-split in `send()`
When an outgoing body contains `[[BUBBLE]]` (or starts with a `[[PHOTOS:`
marker), `send()` splits the text on `[[BUBBLE]]` lines and walks the segments
in order, posting each as its own separate iMessage. Between segments (never
before the first, never around a `[[PAUSE]]`) it `await asyncio.sleep(
INTER_BUBBLE_SECONDS)` so the bubbles land at a human cadence instead of all at
once.

### 3. `[[PAUSE]]` cadence
A segment that is exactly `[[PAUSE]]` emits **nothing** — `send()` does
`await asyncio.sleep(PAUSE_SECONDS)` in place and moves on. This is what gives
the intro its two deliberate reading beats (after the photo stack, and after
the Latch link) without any owner-visible text.

### 4. `[[PHOTOS:...]]` in-band ordered photo stack
- `_parse_photos_marker(chunk)` — recognizes a segment of the form
  `[[PHOTOS:/abs/a.png|/abs/b.png|...]]`, splits on `|`, drops paths missing on
  disk (with a warning), and returns the valid absolute paths.
- Because core never sees or strips this marker, it reaches `send()` **in
  position** inside the ordered `[[BUBBLE]]` walk, so the photos post exactly
  where the SKILL placed them (right after "want to see the kind of thing I
  mean?") instead of being batched to the end of the turn.
- `_declare_and_upload(http, chat_id, path, filename=None)` — declares +
  uploads one image, returning its attachment uid.
- `_post_photo_stack(http, chat_id, paths)` — uploads `paths` and posts them as
  a single stacked "N Photos" message, chunked to the per-message cap. Shared
  by both the in-band `[[PHOTOS:...]]` marker and the real `MEDIA:` batch path
  so both use identical declare/upload/cap/fallback logic. Path-based (not
  `(url, alt)`-based) so it works from `send()`, which only has absolute paths.

### 5. `send_multiple_images(...)` override
Overrides the base adapter so a real multi-image `MEDIA:` batch also routes
through `_post_photo_stack` (one declare/upload/cap/fallback path for both
entry points).

### 6. Attachment cap + 422 safety fallback
- `MAX_ATTACHMENTS_PER_MESSAGE = 4` — up to 4 images ride in ONE message, which
  iMessage renders as a collapsed "4 Photos" stack. Larger batches are chunked
  into groups of ≤ 4.
- This must stay ≤ the Plow API's `MAX_ATTACHMENTS_PER_MESSAGE`; the API 422s
  any message that exceeds it. The API is being bumped **3 → 4**
  (`plow-pbc/plow` PR #1726). **Until that deploy lands**, a 4-attachment post
  422s, and the fallback (`_fallback(reason)` inside `_post_photo_stack`)
  degrades the group to individual images via `_send_attachment` per image —
  still in the right position, nothing silently dropped. Once cap-4 is deployed
  to `api.plow.co`, the four images collapse into the single "4 Photos" stack.

## Note
The extracted stock file and the modified file differ by **+254 / −15** lines
(patch is `handoff/plugin-changes.patch`). Everything above is additive around
existing `send()` / attachment logic; no stock behavior is removed beyond the
small edits the diff shows.
